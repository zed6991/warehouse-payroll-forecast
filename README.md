# Warehouse payroll forecast model

A monthly Excel model that forecasts warehouse payroll, hours and productivity for 8 regional distribution centres and 2 intermediary distribution centres (IDCs), Jan 2025 to Dec 2028.

A [simple version](simple/README.md) of the model is in `simple/`, for comparison. It uses the same month last year for every forecast rate and has fewer tabs.

A [CPLH-driven version](cplh-driven/README.md) is in `cplh-driven/`. It is built from the simple version but turned around: CPLH and cases are the inputs, and it works out the payroll % of sales they need.

**All data in this repo is synthetic.** It is generated by `build_model.py` and does not represent any real company. The site codes (NSW-1, VIC-1, IDC-NSW and so on) are made up.

## Why this model exists

Warehouse payroll is usually budgeted top-down, as a percentage of sales. That gives a dollar number, but it doesn't tell you whether the warehouse can actually do the work for that money.

Operations doesn't manage dollars directly. It manages **hours** (how many people are rostered) and **productivity** (how many cases each person picks in an hour). This model turns the payroll budget into those terms, so you can see what the budget really asks of each site:

- How many hours can we afford?
- How many cases will we need to pick?
- So how productive do we need to be, and is that realistic?

## The core idea

```
Sales  x payroll %   = Total payroll
Total payroll - leadership = Staff payroll
Staff payroll / cost per hour = Hours we can afford

Sales  x cases per $ = Cases we will need to pick

Cases / Hours = CPLH (cases per labour hour): the productivity the budget implies
```

The payroll % comes from the plan. Everything else (cases per $ of sales, cost per hour, leadership share) comes from each site's own recent actuals.

## How it works, step by step

An example for one region in one month:

| Step | Calculation | Result |
|---|---|---|
| 1. Sales | From the plan | $150.0m |
| 2. Total payroll | $150m x 2.0% plan payroll % | $3.00m |
| 3. Leadership payroll | $150m x 0.21% (recent leadership share of sales) | $0.32m |
| 4. Staff payroll | $3.00m - $0.32m | $2.68m |
| 5. Cost per hour | Recent average, adjusted for this month's public holidays and wage increases | $66 |
| 6. Hours | $2.68m / $66 | 40,600 hours |
| 7. Cases | $150m x 0.021 cases per $ of sales, from the Cases_Forecast tab | 3.15m cases |
| 8. CPLH | 3.15m cases / 40,600 hours | 77.6 cases an hour |
| 9. Cost per case | $3.00m / 3.15m cases (total payroll, including leadership) | $0.95 |

How to read it: the plan gives this site $2.68m for staff. At $66 an hour that buys 40,600 hours. Picking 3.15m cases in 40,600 hours means running at 77.6 cases an hour. If the site ran at 72 last year, the plan quietly assumes an 8% productivity gain. The model makes that assumption visible.

Cost per hour uses staff payroll only, because only staff hours are counted. Leadership is salaried, so including it would inflate the cost of each hour worked. Cost per case uses total payroll, because it answers "what does it cost to move a case", and leadership is part of that cost.

Every site tab shows these columns for every month, with actuals up to the last actual month and the forecast after it.

## Where the rates come from

Cases per $ of sales, cost per hour and leadership % of sales are not typed in. They are worked out from each site's actuals in two parts:

1. **Seasonal shape** (last 12 actual months): each calendar month compared with the 12-month average. December might be 1.06, February 0.99.
2. **Level** (last 6 actual months): the average of those months, after dividing out their seasonal index.

The forecast for a month is **level x that month's seasonal index**.

**Why it's done this way:**
- The last 6 months show how the site runs *now*, and averaging 6 months smooths out one-off noise.
- 12 months are needed to see each calendar month once, so that's where the shape comes from.
- Dividing out the seasonal index before averaging stops a busy month from skewing the level. Without it, a 6-month window that includes December would set the level too high for every month after.
- Each rate can also drift by a yearly trend. See [Yearly trends](#yearly-trends).

## Public holidays and wage increases

Cost per hour moves for two reasons that have nothing to do with how well a site runs:

- **Public holidays.** Fewer people work, but those who do are paid penalty rates, so the average cost per hour goes up.
- **Wage increases.** Every hour costs more from the date they take effect.

If the model just averaged actual cost per hour, it would bake last year's Easter or last year's wage level into the forecast. Instead it:

1. **Strips both out of the actuals.** Actual cost per hour is divided by that month's public-holiday factor and wage index, which leaves a "clean" cost per hour.
2. **Takes the run rate** on the clean number (as above).
3. **Adds them back** for each forecast month, using that month's own holidays and the wage increases in force by then.

So if Easter moves from April to March, or a 4.5% increase starts on 1 January, the cost lands in the right month.

**Public-holiday factor**, for example a 30-day month with 2 public holidays, where half the normal hours are worked on a holiday at 250% pay:

```
(28 normal days + 2 holidays x 0.5 of the hours x 2.5 pay)  /  (28 + 2 x 0.5)  =  30.5 / 29  =  1.052
```

So cost per hour is 5.2% higher than in a month with no holidays. The share of hours worked and the pay loading are inputs. Holidays are listed by state on the Holidays tab, generated by rule. You can add, move or delete rows there.

**Wage index**: each increase multiplies the one before. A 4.0% increase in Jan 2026 and a 4.5% increase in Jan 2027 give an index of 1.040 x 1.045 = 1.087 from Jan 2027.

## IDCs

The two IDCs (intermediary DCs) have no sales of their own.

- **Payroll** uses the host region's sales: IDC-NSW uses NSW-1, IDC-VIC uses VIC-1. The plan payroll % for an IDC is a % of its host's sales.
- **Cases** follow the combined sales of every region the IDC ships to: IDC-NSW serves NSW-1 + NSW-2, and IDC-VIC serves VIC-1 + VIC-2. (This was added after the first version. See [IDC volume](#idc-volume-from-every-region-served).)

The National tab adds up payroll, hours and cases for all 10 sites, but takes sales from the 8 regions only. IDC sales would count the host's sales twice.

## Scenarios

The Inputs tab has Base, Upside and Downside scenarios, each with a sales lever and a cases lever (e.g. +3% sales, +2% cases). Pick one from the dropdown and every forecast month moves. Payroll follows sales, because payroll % is the driver. Cases follow sales plus the cases lever, so the CPLH the plan needs also changes.

## Actuals vs forecast

One cell drives everything: **Last actual month** on the Inputs tab. Months up to and including it show actuals from Data_Actuals. Later months show the forecast. The run rates always use the months just before it, so rolling the model forward is:

1. Paste the new actuals into Data_Actuals (one row per site per month, keep the column order). There is room for 5,000 rows.
2. Paste the updated plan (sales forecast and payroll % of sales) into Plan_Inputs.
3. Move **Last actual month** forward.
4. Review the Cases_Forecast tab, and clear adjustments or overrides for months that are now actuals.
5. Check that the Checks tab says **ALL CHECKS OK**.

## Added after the first version

The sections below were built one at a time on top of the first version, in this order.

### Yearly trends

**Why:** in the first version, run rates stayed flat forever. That overstated 2027-28 cases, because price inflation means each dollar of sales buys fewer cases every year.

**How:** each run rate (cases per $, cost per hour, leadership) has a yearly trend on the Inputs tab, applied from the last actual month:

```
Forecast rate = level x seasonal index x (1 + trend) ^ (years after last actual month)
```

The default is -1.5% a year on cases per $ and 0% on the others. Cost per hour already gets wage increases separately, so its trend is only for other drift.

### Bottom-up cross-check

**Why:** payroll % of sales drives the model, so CPLH just falls out of it. A plan could quietly need a 15% productivity jump and nothing would flag it.

**How:** each site also works out what payroll *would* be if it kept last year's productivity:

```
Hours needed        = forecast cases / (CPLH in the same month last year x (1 + productivity target))
Bottom-up payroll   = hours needed x forecast cost per hour
Gap                 = plan staff payroll - bottom-up payroll
```

With the example above, if last year's CPLH was 72: 3.15m / 72 = 43,750 hours x $66 = $2.89m. The plan gives $2.68m, so the gap is **-$0.21m**. A negative gap means the plan is tighter than last year's productivity can deliver.

- The productivity target (default 0%) is on the Inputs tab, e.g. +2% if the site is expected to improve.
- The National tab shows the gap by site and year.
- The Checks tab warns when forecast CPLH moves more than a tolerance (default 10%) from the same month last year.

### IDC volume from every region served

**Why:** an IDC ships to more than its host region. Driving its cases from the host's sales alone missed the volume going to the other region.

**How:** IDC cases now follow the combined sales of the regions it serves (IDC-NSW: NSW-1 + NSW-2, IDC-VIC: VIC-1 + VIC-2). The cases per $ rate is measured against that combined sales figure too. IDC payroll % still applies to the host region's sales, as in the plan.

### Dashboard

**Why:** 10 site tabs with 48 rows each are hard to scan.

**How:** pick National or any site from the dropdown, and six charts update: total payroll, hours, CPLH, cost per hour, cost per case and payroll % of sales. Actuals are blue and the forecast is orange, so a jump at the switch-over point stands out. A bar chart shows the bottom-up gap by site for FY2027 and FY2028.

### Backtest

**Why:** a forecast method should be tested on months where the answer is already known.

**How:** set **Last actual month** earlier (e.g. Mar 2026). The model then forecasts months that already have actuals, and the Backtest tab compares the two, with the mean absolute error for cases, hours, staff payroll, leadership and CPLH. Set it back afterwards.

### Leadership forecast method

**Why:** leadership pay doesn't really grow with sales. It's a fixed team that gets wage increases.

**How:** a switch on the Inputs tab picks between:
- **% of sales** (the default, as in the first version): leadership grows with sales.
- **$ + wage increases**: recent leadership dollars (seasonally adjusted, with past wage increases stripped out) stepped up by each wage increase.

### Using your own site codes

**Why:** the published model uses made-up codes, but you may want to run it with your own.

**How:** type your codes in the **Code** column of the Sites table on the Inputs tab. Everything that matches on site code reads from that column: the sample data, Checks, the National summary, the Dashboard dropdown and each site tab's title. Change a code there and the whole workbook follows.

- **Tab names are optional.** You can rename the site tabs to match the new codes. Excel updates every formula that points at a renamed tab.
- **Real actuals:** paste them into Data_Actuals and Plan_Inputs with the same codes you typed on the Inputs tab. The paste replaces the sample rows, which are formulas pointing at the Code column.
- **For the rebuilt file:** edit the `SITES`, `SERVED` and `PARAMS` codes at the top of `build_model.py` and run it again. That renames the tabs too.

### Cost per case includes leadership

**Why:** cost per case should show the full warehouse labour cost of moving a case. Leadership is part of that cost, even though it is not part of the cost of an hour worked.

**How:** cost per case is now total payroll / cases ($0.95 in the example, up from $0.85 for staff only). Cost per hour is unchanged: staff payroll / staff hours. The bottom-up check uses cost per hour, so it is unaffected.

### Cases forecast tab

**Why:** sales and payroll % are given by the plan and don't change, but cases need judgement: a new store, a range change or volume moving between sites won't show up in a run rate. Cases also needed one place where they can be reviewed and changed without touching the formulas on the site tabs.

**How:** the Cases_Forecast tab has months down the side and one column per site, in four blocks:

1. **Run-rate forecast**: volume driver sales x cases per $ run rate x (1 + scenario cases lever), worked out as before. Actual months show actual cases.
2. **Adjustments**: type extra cases (or a negative number) for a site and month. They are added to the run rate.
3. **Override**: type the cases you want for a site and month. They replace the run rate and the adjustment.
4. **Cases forecast used**: the override if there is one, otherwise run rate + adjustment. This is what feeds *Cases picked* on each site tab, and from there CPLH, cost per case and the dashboard.

Adjustments and overrides are separate yellow input cells, so typing in them never overwrites a formula. Clearing a cell puts the model value back. Anything typed in an actual month is ignored, and the Checks tab warns about it.

Payroll doesn't change when cases change, because payroll still comes from sales x plan payroll %. What changes is the CPLH the plan implies: more cases for the same hours means the site has to be more productive.

### CLR (placeholder)

A CLR tab for cost-saving initiatives (initiative, site, type, value, start month, ramp-up, end month, active). It is a placeholder for now. Nothing on it feeds the forecast yet.

## Workbook tabs

- **README**: how to update and how the logic works
- **Inputs**: last actual month, scenario switch, wage increases, public-holiday assumptions, site list, trends, productivity target, leadership method, site codes
- **Data_Actuals**: actuals in long format (one row per site per month). Paste over it to update.
- **Plan_Inputs**: sales forecast and payroll % of sales per site per month
- **Cases_Forecast**: run-rate cases, your monthly adjustments and overrides by site, and the cases used
- **CLR**: placeholder for cost-saving initiatives (not linked yet)
- **Holidays / Calendar**: public holidays by state, PH cost factor, wage index
- **Checks**: data coverage and reconciliation checks, plus CPLH warnings
- **Dashboard**: site selector and charts
- **Backtest**: forecast vs actual when the last actual month is set earlier
- **National**: all sites added up, plus site-by-year summaries
- **One tab per site**: drivers and metrics on the left, helper columns (actuals, run rates, plan) in grey on the right

Colours: yellow cells with blue text are inputs. Blue-shaded rows are forecast months.

## Build

```bash
python3 -m venv .venv
.venv/bin/pip install openpyxl
.venv/bin/python build_model.py
```

This outputs `warehouse_payroll_forecast.xlsx`. The workbook recalculates when it opens.

## Status

Backtest on the synthetic data (forecasting Apr-Sep 2026 from Mar 2026): mean absolute error of 1.0% on cases, 0.4% on hours and 1.4% on CPLH. The synthetic data was generated with logic similar to the model's, so this proves the mechanics, not the method. Real actuals are the real test.

Not yet done: a split by chamber (ambient / chiller / freezer), scenario levers per region, and forecasting past Dec 2028.
